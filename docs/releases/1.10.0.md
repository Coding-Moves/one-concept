# One Concept 1.10.0 release checklist

Release target: `develop` → `main`. This is a native release: marketing version
and runtime are **1.10.0**. The previous runtime is 1.3.0. The Expo native module
updates require a new APK; existing 1.3.0 installations do not receive the new
runtime through OTA. Keep their API contract working during the transition.

## User-visible changes

- Permanent streak achievements, including credit for past qualifying streaks.
- Profile collection, next milestone, and grouped celebrations that wait for the
  What's New card to close. Earned badges survive a later break in the streak.
- Public privacy policy linked from About.
- Dependency updates include Expo SDK 57 fixes, React Navigation, XML parsing,
  PyJWT, Uvicorn and SQLAlchemy. Native fixes take effect in the new binary.

The matching What's New entry uses the existing device-level version dismissal.
It appears for 1.10.0 and remains dismissed on subsequent launches after “Got it”
when device storage succeeds. Clearing app data or reinstalling can show it again.

## Before opening the release PR

1. Merge the version/card preparation PR into develop after owner confirmation.
2. In the **production** Supabase SQL Editor, apply
   [0016_achievements.sql](../../backend/migrations/0016_achievements.sql) if it
   has not already been applied. It creates two RLS-protected tables, nine
   definitions and historical awards in one transaction. Review the normal
   backup/recovery procedure first. Do not rerun the create-table migration if
   it is already present; inspect its schema instead.
3. Run the read-only inspection below. Both tables must be present with RLS;
   policies must allow SELECT only, with own-user filtering on awards; definitions
   must show the nine thresholds 7, 30, 90, 180, 365, 500, 1000, 5000, 10000.
   Inspect the displayed keys/checks and columns against the migration. Historical
   awards may legitimately be empty if nobody qualified; record the aggregate
   count without sharing user records.
4. Only after actual production application and verification, append
   `0016_achievements.sql` to
   [applied.txt](../../backend/migrations/applied.txt). Until then the required
   **Migrations applied check** must remain blocked. Do not mark it applied merely
   because local PostgreSQL tests passed.
5. Verify the final develop-to-main diff includes both `expo.version: 1.10.0`
   and the nonempty 1.10.0 What's New entry. Include native-runtime implications,
   validation and outstanding device checks in the release PR description.

```sql
begin read only;
select c.relname, c.relrowsecurity
from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public'
  and c.relname in ('achievement_definitions', 'user_achievements');
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname = 'public'
  and tablename in ('achievement_definitions', 'user_achievements');
select table_name, column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_schema = 'public'
  and table_name in ('achievement_definitions', 'user_achievements')
order by table_name, ordinal_position;
select conrelid::regclass as table_name, conname, pg_get_constraintdef(oid)
from pg_constraint
where conrelid in ('public.achievement_definitions'::regclass,
                   'public.user_achievements'::regclass);
select code, metric, threshold, name, artwork_key, sort_order
from public.achievement_definitions order by sort_order;
select source, count(*) as award_count
from public.user_achievements group by source;
rollback;
```

## After release PR approval and separately confirmed merge

1. Main triggers Railway deployment. Keep generation paused during any worker
   transition; verify API and workers are running the exact merged main SHA.
2. Check `/health`, `/privacy`, authentication/recovery, daily lessons and
   reviews, collection/acknowledgement and historical badges using a test account.
   Confirm existing runtime 1.3.0 clients still complete lessons and reviews.
3. Confirm EAS preview/production endpoint configuration and Android signing/push
   credentials. The presence of the GitHub `EXPO_TOKEN` secret alone does not
   prove it is valid or that a cloud build will succeed.
4. Run **Release** manually on main with the verified 40-character backend SHA.
   Its guard rejects another branch or revision. It publishes updates to runtime
   1.10.0, creates v1.10.0 and dispatches **Release APK**. The runtime change opens
   the native build gate; it uses `production-apk` and the production channel.
5. Wait for the EAS build and stable `apk-latest/one-concept.apk` upload to finish.
   A GitHub tag or successful OTA job alone is not proof the APK was built.
6. Install the new APK. Verify the 1.10.0 What's New card, dismissal after restart,
   achievement ordering, signed-in upgrade, offline viewing/sync, Android Back,
   TalkBack/font scaling, and push permission, receipt and tap behavior.
7. Resume generation only after backend/worker and content checks pass. Monitor
   auth, completions, reminder failures and achievements after rollout.

If a build/publication step fails, keep the previous known-good APK available.
Do not send new-runtime JS to runtime 1.3.0 as a workaround. Avoid reverting or
removing additive production migration 0016 simply to roll back the API.
